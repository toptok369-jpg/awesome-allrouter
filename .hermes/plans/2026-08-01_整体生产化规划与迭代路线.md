# TopTok 整体生产化规划与迭代路线

> 文档日期：2026-08-01
>
> 文档性质：TopTok 生产化的统一基线。历史交接中“已验证”“当前实测”“未验证”必须严格区分；后续每次迭代都要补充证据，不得用代码存在、HTTP 200、ComfyUI 成功或存在媒体文件代替商用验收。

## 1. 目标

把 TopTok 从“产品功能、角色资产、多个实验视频管线分别可运行”推进到一个真实用户愿意付费、付费后能稳定收到合格内容的生产系统。

最终用户旅程必须完整：

```text
访问站点
  -> 18+ 门禁
  -> 浏览真实角色和预览内容
  -> 连接钱包 / 建立访客会话
  -> 创建或选择角色
  -> 明确看到价格、交付物、预计等待时间和失败退款规则
  -> 支付
  -> 看到任务状态和可解释进度
  -> 获得本人角色的合格图片/视频/语音资产
  -> 预览、下载、再次购买或继续私聊
```

目标不是证明某个模型“能出图”，而是证明：

- 用户知道买什么；
- 用户愿意为结果付款；
- 支付后任务不会静默丢失；
- 生成失败不会显示完成；
- 成品人物、服装、动作、声音和时长达到交付标准；
- 失败可以重试、退款或人工处理；
- 每一个结果都能追溯到输入资产、工作流、模型、参数和质量报告。

## 3. 当前问题分层

### P0：不解决就不能声称商用

1. **没有统一的生产任务契约**
   - 产品任务、Comfy prompt、DramaClaw 任务、作者 graph 和最终资产之间没有统一 manifest。
   - 失败阶段、重试边界、取消、退款和交付状态不能完全追踪。

2. **生产 moderation 仍是 stub**
   - 18+ 门禁不是内容安全审核。
   - 必须有文本、图片、视频的生产审核 provider 和明确失败策略。

3. **支付到交付闭环仍需真实验收**
   - 必须验证支付成功、任务创建、异步恢复、生成、质量门禁、交付、失败重试和退款/人工介入。

4. **没有一条通过完整商用门禁的一分钟成片**
   - 当前记录为 A 线 5 条不合格、B 线 1 条冒烟不合格、C 线 0 条。
   - 目标 A/B/C 各 3 条，当前 `0/9`。

5. **资产一致性仍未闭环**
   - 展示图服装不稳定；
   - 三视图继承动态动作；
   - signature 有俯拍腿变形；
   - 头像可能与第一张 seed 重复；
   - 角色脸和造型没有完全通过 visual state 分层。

6. **GPU 调度和隔离语义不明确**
   - 18191 与主 ComfyUI 的关系需要固定记录；
   - 三条视频线不能并行；
   - 必须使用串行、显存感知队列。

### P1：不解决会导致用户体验差、成本高或难以维护

- 通用 Comfy provider 与作者固定 graph 并存但职责边界不清；
- C 线 DramaClaw fork 和 alias shim 的维护面过大；
- 生产目录存在 `.bak`、`.orig` 和一次性脚本，部署来源不唯一；
- `ensureFan()` 可能静默创建访客，掩盖鉴权错误；
- 服务端密钥虽然已注入，但缺少启动时强校验；
- LLM fallback、上游模型和请求 ID 没有统一可观察性；
- 质量报告没有全部展示到用户和运营后台；
- 低质量资产的重试策略还未按失败原因分类。

### P2：可以在核心交付稳定后优化

- C 线进一步产品化；
- 更多作者工作流；
- 复杂的营销自动化；
- 大规模角色批量生成；
- 多平台内容分发。

## 4. 目标架构

```text
TopTok UI
  -> ProductOrder / CreationJob
  -> AssetPlanner
       -> CharacterCanonical
       -> VisualState
       -> SceneCard / PropCard
       -> Storyboard
  -> WorkflowRouter
       -> Krea2Provider
       -> IdentityEditProvider
       -> A01Provider
       -> B01Provider
       -> BerniniProvider
       -> DramaClawPlanner
  -> SerialGpuQueue
  -> Comfy/DramaClaw adapter
  -> QualityGate
       -> media streams
       -> duration / resolution / aspect ratio
       -> loudness / audio sync
       -> identity / face / anatomy / sharpness
       -> adult fictional character / moderation
       -> story and asset contract
  -> ArtifactManifest
  -> Delivery / Preview / Download
  -> Payment ledger / refund / audit
```

### 4.1 统一工作流契约

新增 `WorkflowProvider` 概念，不把固定作者 graph 塞入简单的通用 `MediaProvider`。

最少包含：

- `workflowId`、`variant`、graph 版本和 sha256；
- 允许替换的节点白名单；
- 输入图、输入视频、prompt、seed、输出前缀；
- `submit`、`poll`、`cancel`；
- Comfy prompt ID；
- 输出文件与 hash；
- 节点错误和阶段错误；
- provider/model/LoRA 实际名称；
- 质量报告和人工验收结论。

### 4.2 统一资产模型

角色不能只存一段 appearance 文本。

```text
Character
  - age >= 21 / fictional flag
  - persona
  - photoPersona
  - faceSpec
  - visualStates[]

VisualState
  - name
  - faceDescription
  - appearanceDetails
  - wardrobeRef
  - neutralFullBodyRef
  - multiViewRef
  - canonicalHash

SceneCard / PropCard
  - description
  - sourceAsset
  - hash
  - approved
```

展示图和视频参考图必须使用不同目的的资产，但共享同一个 `faceSpec` 和 `visualState`。

### 4.3 用户可感知的任务状态

用户不能只看到“生成中”。应显示：

- 已收到订单；
- 正在准备角色资产；
- 正在生成镜头 3/15；
- 正在检查人物一致性；
- 正在检查音频和时长；
- 通过后交付；
- 失败原因、自动重试次数和人工处理状态。

任何质量门禁未通过，任务不能显示“完成”。

## 5. 分阶段执行计划

### 阶段 0：建立可回滚基线

目标：以后所有改动都可定位、可回滚、可比较。

动作：

1. 保存线上 `/app` 的 Git commit、构建时间、文件清单和配置变量名；不保存 secret 值。
2. 保存 4090 主机 ComfyUI、18191、18192 的 `system_stats`、`object_info`、队列和模型引用报告。
3. 为生产 graph 计算 sha256。
4. 保存当前数据库 schema/迁移版本和 Redis 连接检查结果。
5. 保存生产入口 `/age`、核心 API、支付回调和健康接口结果。
6. 建立 `production-baseline-YYYYMMDD` 标签或不可变归档。

完成定义：任何人可以回答“当前生产运行的是什么版本、什么 graph、什么模型、什么配置”。

### 阶段 1：统一任务与质量门禁

目标：先让系统不会把失败伪装成成功。

动作：

1. 定义 `ArtifactManifest` 和 `WorkflowJob` 数据结构。
2. 让所有图片、视频和短剧任务写 manifest。
3. 将节点错误、超时、无资产、无声、时长不足、身份失败映射到明确错误码。
4. 把单镜和全片质量门禁接入订单状态机。
5. 增加重试上限、失败原因和人工接管状态。
6. 生产启动时拒绝 stub moderation、开发 secret、缺失数据库/Redis/Comfy 配置。

完成定义：任何任务都能在后台追踪，从支付到最终资产的每一步均有记录。

### 阶段 2：角色资产生产化

目标：生成出来的角色值得用户点击并且可稳定复现。

动作：

1. canonical 先生成中性、闭嘴、手自然下垂的全身基准。
2. visual state 分离脸、服装、身体和场景。
3. 展示图第一张锁定 visual state，第二、三张引用第一张和人物卡。
4. 视频三视图逐个生成再拼接，禁止直接让模型一次画四视角。
5. 头像单独生成或裁切，禁止与 seed[0] 共用资源哈希。
6. signature 使用平视或轻微低机位，禁止俯拍变形。
7. photoPersona 只负责生活感、拍摄者、地点、相机和行为，不负责锁服装。
8. portrait QC 失败时按 purpose 精确重试，不盲目全部重生成。

完成定义：同一角色三张展示图具有亲和力且服装一致；视频人物卡中性、清晰、无动态残留。

### 阶段 3：A 线先达成第一条商用片

目标：用最短路径得到可付费交付的第一条一分钟短片。

固定约束：

- 15 镜，每镜约 4.0417 秒，总时长约 60.6 秒；
- 9:16；
- 固定作者参数，不擅自修改模型、节点、LoRA 强度；
- Krea2 双路参考：场景板 + 人物卡；
- b01 音视频分支承载口型和声音；
- `continue` 不接道具/手部特写；
- 连续段最多 3 镜，之后回到身份 anchor；
- 所有场景和道具必须来自已批准资产卡。

完成定义：一条片同时通过单镜门禁、全片门禁、人工观看和付费用户交付回归。

### 阶段 4：支付、交付和真实用户体验

目标：模拟真实用户完整付费。

测试场景：

1. 新用户过 18+ 门禁；
2. 创建角色并看到预览；
3. 看到明确价格和预计等待时间；
4. 支付成功；
5. 刷新、重启服务后任务继续；
6. 生成中能看到进度；
7. 成功后只能下载通过门禁的资产；
8. 模拟失败，看到可解释错误和重试/退款路径；
9. 私聊语音、展示图、短剧交付互不串资产；
10. 账单和交付记录可在后台对账。

完成定义：从用户视角流程无死路，付费后不会遇到“支付成功但没有作品”。

### 阶段 5：B 线和 C 线扩展

B 线：

- 先取得合法授权动作源，或建立自有动作素材库；
- 用完整单人 Bernini graph 做单镜替换；
- 通过后接 LTX 口型和声音；
- 残缺双人 S2V graph 暂不投入生产。

C 线：

- 保留 DramaClaw 的导演规划、visual state 和项目归档思路；
- 将媒体生成收敛到 TopTok WorkflowProvider；
- alias shim 只作为过渡，不作为长期核心依赖；
- 不再扩大 editable fork，先固定 patch、版本和回滚方案。

## 6. 第一轮实际优化任务

第一轮不追求一次改完全部功能，优先完成以下闭环：

1. 线上生产基线快照和版本记录；

8. 生产后台显示 provider、workflow、prompt ID、门禁和失败原因。

每一步都必须：

- 访问真实 HTTP 入口；
- 对 GPU 任务串行执行；
- 任务完成后保存 manifest 和媒体质量报告。

## 7. 商用验收标准

### 图片

- 明确为虚构成年人，年龄结构化字段 >= 21；
- 单人、脸清晰、自然比例、无文字/logo/watermark；
- identity / signature / story 三张身份一致；
- 展示图有生活感和亲和力，不是三张模板化时尚大片；
- 服装满足购买时选择的 visual state。

### 视频

- 时长 55–70 秒，目标 60 秒；
- 竖屏 9:16，编码可播放；
- 人物全片身份稳定；
- 服装、场景、道具连续；
- 动作和人体合理；
- 音轨存在且有效，响度达到门禁；
- 台词与音频转写一致；
- 有台词时口型可见且不依赖后期叠音冒充；
- 字幕错误能被检测并处理；
- 全片人工观看通过。

### 产品与支付

- 无权限无法下载原始付费资产；
- 支付成功与任务创建幂等；
- 服务重启后任务恢复；
- 失败不能显示完成；
- 有重试、退款或人工介入；
- 运营后台可按订单、角色、workflow、prompt ID、资产 hash 对账。

## 8. 风险与停止条件

以下情况必须暂停扩量，不得继续生成 9 条：

- 第一条片不能通过完整门禁；
- 支付成功后任务状态无法恢复；
- moderation 仍是 stub；
- 生产代码和部署代码来源不一致；
- GPU 任务并发导致 OOM；
- 质量失败原因无法归类；
- 关键秘密仍写在脚本、日志或交接文档中；
- 资产和订单无法完成 hash 级追踪。

## 9. 统一进度指标

每次迭代只记录真实证据：

- `commercial_clips_passed`: 通过商用验收的成片数；
- `payment_to_delivery_passed`: 支付到交付完整回归数；
- `identity_gate_pass_rate`: 身份门禁通过率；
- `audio_gate_pass_rate`: 音频门禁通过率；
- `job_recovery_pass_rate`: 重启恢复通过率；
- `failed_jobs_with_reason`: 有明确失败原因的失败任务比例；
- `unresolved_p0`: 未解决 P0 数量。

当前基线：

```text
commercial_clips_passed = 0
payment_to_delivery_passed = 未完成真实回归
A/B/C = 0/0/0 商用成片
moderation = stub，不合格
```

后续任何“已完成”都必须附：时间、版本、任务 ID、文件路径或公开 URL、实际命令输出摘要和验收结论。
